## Chapter 12-2 동기화 기법

주요 키워드: 뮤텍스 락, 세마포, 모니터

> Q. 세마포어랑 뮤텍스 락이랑 아무튼 숫자를 - -하거나 ++ 하는 건 똑같은데 왜 함수 명이 다를까?

이름이 다른 이유의 5할은 “관습”이고 나머지 5할은 “완전히 똑같지 않기 때문”이다.

|                            | 세마포어 (Semaphore)                                       | 뮤텍스 (Mutex)                                                           |
| -------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------ |
| **값의 범위**              | 정수 (0, 1, 2, 3... 카운팅 가능)                           | 이진 (잠김/열림, 딱 2가지 상태)                                          |
| **용도**                   | **자원의 개수**를 세는 것 (예: 프린터 3대 중 몇 대 남았나) | **상호 배제** (딱 1개의 자원을 놓고 서로 못 들어가게)                    |
| **소유권(ownership) 개념** | **없음** — A가 wait() 했는데 B가 signal() 해도 됨          | **있음** — 잠근 애만 풀 수 있음 (락을 안 건 프로세스가 unlock 하면 에러) |
| **누가 몇 번 부르나**      | 여러 프로세스가 동시에 여러 번 wait/signal 가능            | 정확히 한 프로세스가 lock 걸고, **그 프로세스가** unlock                 |

개념이 살짝 다른 이유 (본질적): 세마포어는 "카운팅 가능한 범용 동기화 도구", 뮤텍스는 "소유권이 있는 이진 락"으로, 뮤텍스는 사실 세마포어의 특수한 경우(초기값 1인 세마포어)에 가깝다. 그래서 락을 걸고 말고의 뮤텍스와 자원의 개수가 몇 개 남았는지를 카운팅하는 세마포어의 특성에서 함수의 이름이 다른 것이다.

> Q. 세마포어는 훌륭한 동기화 도구인 것 같은데, 왜 모니터가 등장하게 된 것일까?

세마포어, 뮤텍스는 사실 도구에 불과하다. 하지만 모니터는 “인간은 왜 동기화를 자꾸 틀리는가”에서 출발한 설계 원칙이다.

문제의 시작: 세마포어(wait(), siganl())의 실수 → 함수를 깜빡 하거나? wait()함수를 두 번 부르거나? → 마치 인간에게 칼을 주고 절대 실수하지마라고 말하는 것과 비슷하다. 이런 규율을 구조로 바꿔낸 것이 모니터이다.

동기화를 프로그래머의 노력에 맡기지 말고, 캡슐화를 적용시켜 언어/컴파일러가 구조적으로 강제하게 만들자라는 아이디어로 등장하게 되었다.
